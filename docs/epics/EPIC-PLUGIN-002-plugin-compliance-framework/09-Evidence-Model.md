# Plugin Compliance Framework

## 09 Evidence Model

### Introduction

The Evidence Model defines how FamilyOS represents, collects, validates, reuses, and governs the information used to support plugin compliance decisions.

Compliance cannot be based solely on assertions.

Every meaningful compliance outcome must be supported by evidence capable of demonstrating why a requirement passed, failed, remained incomplete, or could not be evaluated.

Evidence therefore forms the factual foundation of the Plugin Compliance Framework.

The fundamental relationship is:

```text
Requirement
    │
    ▼
Validation
    │
    ▼
Evidence
    │
    ▼
Rule Evaluation
    │
    ▼
Compliance Decision
```

---

## Purpose

The Evidence Model provides a common representation for compliance information produced by different engineering systems.

It enables FamilyOS to:

* normalize validator output;
* preserve evidence provenance;
* verify evidence freshness;
* assess evidence trust;
* reuse compatible evidence;
* prevent stale evidence from satisfying current requirements;
* correlate evidence with rules;
* support auditability;
* support certification workflows;
* preserve historical compliance context.

The model must support both locally generated evidence and evidence produced by trusted external engineering systems.

---

## Evidence Principle

The governing evidence principle is:

> A compliance decision is only as trustworthy as the evidence supporting it.

Evidence must therefore be:

* identifiable;
* attributable;
* contextual;
* traceable;
* sufficiently fresh;
* compatible with the validation context;
* protected from silent mutation.

The framework must never treat arbitrary plugin claims as trusted evidence without validation.

---

## Evidence Definition

Compliance Evidence is a structured representation of an observation, measurement, validation result, or verified declaration relevant to one or more compliance rules.

A conceptual model is:

```text
ComplianceEvidence
├── id
├── type
├── source
├── producer
├── producer_version
├── plugin_id
├── plugin_version
├── source_revision
├── platform_version
├── framework_version
├── created_at
├── scope
├── trust
├── payload
├── integrity
└── metadata
```

The exact physical schema may evolve.

The semantic requirements must remain stable.

---

## Evidence Identity

Every evidence object should have a unique identity.

Evidence identity allows:

* rule correlation;
* finding correlation;
* report references;
* reuse tracking;
* audit history;
* certification references.

An Evidence ID identifies one evidence artifact or observation.

It must not be confused with:

* Rule ID;
* Finding ID;
* Evaluation ID;
* Plugin ID.

---

## Evidence Types

Evidence must be categorized by type.

Initial evidence types may include:

```text
IDENTITY
METADATA
STRUCTURE
ARCHITECTURE
CAPABILITY
CONTRIBUTION
DEPENDENCY
CONFIGURATION
SECURITY
TEST
QUALITY
DOCUMENTATION
COMPATIBILITY
LIFECYCLE
GOVERNANCE
```

Additional technical evidence types may exist within these broader categories.

---

## Evidence Source

The evidence source identifies the system, artifact, or observation from which evidence originated.

Examples include:

* plugin manifest;
* plugin metadata;
* source tree;
* import graph;
* dependency graph;
* capability registry;
* contribution registry;
* configuration schema;
* test suite;
* static analysis;
* runtime execution;
* documentation;
* CI artifact;
* manual review.

Source information must remain visible to compliance consumers.

---

## Evidence Producer

The producer identifies the tool or process that created the evidence.

Examples may include:

```text
familyos-compliance
pytest
mypy
ruff
familyos-runtime
familyos-build
familyos-release
manual-review
```

Producer identity should include version information whenever that version can affect evidence interpretation.

---

## Producer Version

Evidence generated by tooling should record the producer version.

For example:

```text
producer: mypy
producer_version: 1.x
```

or:

```text
producer: familyos-compliance
producer_version: 1.0.0
```

Tool versioning supports reproducibility and compatibility analysis.

---

## Plugin Association

Every plugin-specific evidence object must identify the plugin to which it applies.

At minimum:

```text
plugin_id
plugin_version
```

Where source-controlled validation is involved, evidence should also identify:

```text
source_revision
```

This prevents evidence from one plugin version from being silently reused for another.

---

## Platform Association

Some evidence is meaningful only relative to a FamilyOS platform version.

Examples include:

* compatibility tests;
* runtime contract tests;
* capability validation;
* lifecycle validation;
* integration tests.

Such evidence must identify the relevant platform context.

---

## Framework Association

Evidence may also depend on the Compliance Framework version.

This is especially important when:

* evidence schemas change;
* validators evolve;
* rule semantics change;
* trust requirements change.

Framework association allows the engine to determine whether existing evidence remains usable.

---

## Evidence Scope

Evidence must define what it proves.

Scope may identify:

* complete plugin;
* file;
* module;
* capability;
* contribution;
* dependency;
* configuration key;
* lifecycle operation;
* documentation section;
* individual rule.

Evidence scope prevents broad interpretation of narrowly collected information.

---

## Scope Principle

Evidence must not be used beyond the scope it can legitimately support.

For example:

```text
Unit Test Evidence
```

may prove behavior of a specific component.

It does not automatically prove:

```text
Complete Plugin Lifecycle Compliance
```

The framework must preserve this distinction.

---

## Evidence Payload

The payload contains the factual data produced by validation.

Examples include:

```text
Manifest schema valid: true
```

```text
Unsupported imports:
  - familyos.runtime.internal.loader
```

```text
Tests passed: 84
Tests failed: 0
```

```text
Documentation sections missing:
  - Compatibility
```

Payload structure should be specific to the evidence type while remaining serializable.

---

## Evidence Metadata

Evidence metadata provides supporting context that does not belong directly to the primary payload.

Metadata may include:

* execution environment;
* operating system;
* Python version;
* command configuration;
* test selection;
* validation options;
* dependency state.

Metadata should be sufficient to understand important environmental influences on evidence.

---

## Evidence Provenance

Provenance describes where evidence came from and how it was produced.

A conceptual provenance chain is:

```text
Plugin Source
     │
     ▼
Validator / Engineering Tool
     │
     ▼
Raw Observation
     │
     ▼
Evidence Adapter
     │
     ▼
Compliance Evidence
```

The framework should preserve enough information to reconstruct this chain.

---

## Provenance Requirements

Trusted evidence should identify:

* producer;
* producer version;
* source;
* source revision where applicable;
* creation time;
* execution context;
* associated plugin;
* associated platform context.

Evidence lacking required provenance may be rejected by stronger compliance profiles.

---

## Evidence Trust

Not all evidence sources have equal trust.

The framework should support an explicit trust model.

A conceptual model may include:

```text
UNVERIFIED
LOCAL
TRUSTED
ATTESTED
```

The exact terminology should be standardized before implementation.

Trust represents confidence in evidence provenance and integrity.

It does not indicate whether the evidence itself represents a pass or failure.

---

## Unverified Evidence

UNVERIFIED evidence may include plugin-provided claims that have not been independently validated.

Examples include:

* self-declared test status;
* manually supplied compatibility claims;
* unsigned external reports.

Such evidence may be useful as input.

It should not automatically satisfy strong compliance requirements.

---

## Local Evidence

LOCAL evidence is generated through recognized tooling in a local development environment.

Examples include:

* local Pytest execution;
* local MyPy execution;
* local Ruff execution;
* local compliance validators.

Local evidence is valuable for development feedback.

Stronger profiles may require higher provenance guarantees.

---

## Trusted Evidence

TRUSTED evidence originates from a recognized controlled engineering process.

Examples may include:

* protected CI pipelines;
* FamilyOS build infrastructure;
* official release workflows.

Trusted evidence should preserve sufficient provenance for independent verification.

---

## Attested Evidence

Future certification workflows may support cryptographically attested evidence.

Attestation may bind:

```text
Evidence
   +
Artifact Identity
   +
Producer Identity
   +
Integrity Proof
```

This can provide stronger guarantees for distributed compliance and certification systems.

Attestation is a future capability, not a prerequisite for the initial framework implementation.

---

## Evidence Integrity

Evidence must be protected from silent modification.

At minimum, finalized evidence should be treated as immutable.

Future integrity mechanisms may include:

* content hashes;
* artifact digests;
* digital signatures;
* signed attestations.

Integrity metadata becomes increasingly important when evidence moves between systems.

---

## Evidence Immutability

Once evidence has contributed to a finalized Compliance Result, it must not be modified in place.

If validation is repeated, new evidence should be produced.

Conceptually:

```text
Evaluation A
   │
   └── Evidence A

Evaluation B
   │
   └── Evidence B
```

Historical evidence remains associated with its original evaluation.

---

## Evidence Freshness

Evidence is valid only while its relevant context remains compatible.

Freshness does not mean merely recent in time.

It means that the evidence still corresponds to the state being evaluated.

Freshness may depend on:

* plugin version;
* source revision;
* dependency state;
* platform version;
* rule version;
* validator version;
* configuration;
* execution environment.

---

## Source Freshness

Source-derived evidence becomes stale when relevant plugin source changes.

For example:

```text
Source Revision A
      │
      ▼
Test Evidence A
```

must not automatically satisfy validation for:

```text
Source Revision B
```

unless the framework can prove that the relevant source scope was unaffected.

---

## Dependency Freshness

Dependency evidence may become stale when:

* dependency versions change;
* lock files change;
* dependency policy changes;
* prohibited package lists change.

Dependency state must therefore participate in freshness evaluation when relevant.

---

## Platform Freshness

Evidence generated against one platform version may not remain valid against another.

For example:

```text
Plugin 1.0
+
FamilyOS 4.0
```

compatibility evidence does not automatically prove compatibility with:

```text
FamilyOS 5.0
```

Platform-sensitive evidence must identify its platform context.

---

## Rule Freshness

Evidence may become insufficient when compliance requirements evolve.

For example:

```text
Rule v1
   │
   ▼
Evidence A
```

may not satisfy a stronger replacement rule.

Rule evolution must therefore participate in evidence compatibility analysis.

---

## Validator Freshness

A validator update may affect evidence interpretation.

Not every validator update invalidates existing evidence.

The framework should distinguish:

* equivalent implementation improvements;
* evidence schema changes;
* semantic validation changes.

Compatibility rules determine whether regeneration is required.

---

## Time-Based Freshness

Some evidence may have explicit time limits.

Examples might include:

* security scans;
* external dependency vulnerability checks;
* manual approvals;
* certification evidence.

Time-based expiration should be rule- or profile-driven rather than globally assumed.

---

## Evidence Compatibility

Before reuse, evidence must be checked against the current Validation Context.

Conceptually:

```text
Existing Evidence
       │
       ▼
Compatibility Check
       │
   ┌───┴────┐
   ▼        ▼
Reusable   Invalid
```

Compatibility should evaluate all relevant dimensions rather than only Evidence ID.

---

## Evidence Reuse

Evidence reuse is encouraged when it preserves correctness.

Reuse can reduce:

* validation duration;
* CI cost;
* duplicate test execution;
* repeated static analysis;
* certification preparation time.

However:

> Reuse is an optimization, never a relaxation of evidence requirements.

---

## Evidence Reuse Conditions

Evidence may be reused only when:

* provenance is acceptable;
* integrity is valid;
* scope matches;
* plugin context matches;
* platform context is compatible;
* evidence remains fresh;
* producer is accepted;
* profile trust requirements are satisfied.

Failure of any required condition must prevent silent reuse.

---

## Evidence Invalidation

The framework must support explicit evidence invalidation.

Typical invalidation triggers include:

```text
Source Change
Dependency Change
Platform Change
Rule Change
Validator Semantic Change
Configuration Change
Evidence Expiration
Integrity Failure
```

Invalidation should identify why evidence is no longer accepted.

---

## Partial Invalidation

Not every plugin change requires invalidating all evidence.

For example:

```text
Documentation Change
```

may not invalidate:

```text
Dependency Graph Evidence
```

The architecture should eventually support scope-aware invalidation.

This enables efficient incremental compliance validation.

---

## Evidence Dependencies

Evidence may depend on other evidence.

For example:

```text
Source Metadata Evidence
        │
        ▼
Capability Discovery Evidence
        │
        ▼
Capability Contract Evidence
```

Evidence dependencies should remain traceable where they affect interpretation.

---

## Raw Evidence

Raw evidence represents direct output from a validator or external tool.

Examples include:

* test result files;
* static analysis output;
* parsed manifests;
* dependency graphs.

Raw evidence may require normalization before it can be consumed consistently by compliance rules.

---

## Normalized Evidence

Normalized evidence converts tool-specific output into the canonical FamilyOS Evidence Model.

Conceptually:

```text
Pytest Output
     │
     ▼
Test Evidence Adapter
     │
     ▼
Normalized Test Evidence
```

Normalization isolates compliance rules from external tool output formats.

---

## Evidence Adapters

Evidence Adapters translate external or native tool results into Compliance Evidence.

Potential adapters include:

```text
Pytest Adapter
MyPy Adapter
Ruff Adapter
Manifest Adapter
Dependency Adapter
Documentation Adapter
Runtime Adapter
```

Adapters must not reinterpret compliance policy.

They normalize factual information.

---

## Adapter Versioning

Evidence adapters should have explicit versions where transformation semantics may change.

Adapter version information supports:

* reproducibility;
* debugging;
* compatibility;
* evidence invalidation.

---

## Evidence Collection Strategies

Evidence may be collected through:

* direct validator execution;
* imported CI artifacts;
* build artifacts;
* runtime observation;
* manual review;
* future remote services.

The collection mechanism must not change the semantic meaning of the resulting evidence.

---

## Direct Evidence

Direct evidence is produced during the current compliance evaluation.

For example:

```text
Compliance Engine
      │
      ▼
Metadata Validator
      │
      ▼
Metadata Evidence
```

Direct evidence naturally shares the current evaluation context.

---

## Imported Evidence

Imported evidence was generated by another process.

Examples include:

* previous CI stages;
* build systems;
* release systems;
* external security scanners.

Imported evidence requires stronger compatibility validation because it originates outside the current execution.

---

## Manual Evidence

Some requirements may require human review.

Manual evidence should still be structured.

A conceptual model may include:

```text
Reviewer
Review Authority
Rule
Decision
Justification
Timestamp
Scope
Expiration
```

Manual evidence must not exist only as an undocumented comment.

---

## Manual Evidence Trust

Profiles may define which reviewers or authorities are accepted for specific rules.

For example:

```text
Architecture Review
```

may require an architecture governance authority.

```text
Security Exception
```

may require security governance approval.

The evidence model provides the representation.

Governance defines the authority.

---

## Evidence and Rules

Evidence and rules have a many-to-many relationship.

One evidence object may support multiple rules.

One rule may require multiple evidence objects.

Conceptually:

```text
Evidence A ─────┬────► Rule 1
                └────► Rule 2

Evidence B ──────────► Rule 2

Evidence C ──────────► Rule 3
```

The framework must preserve these associations.

---

## Evidence Requirements

Rules define what evidence they require.

The Evidence Model determines whether candidate evidence satisfies those requirements.

A rule may require:

```text
one evidence type
```

or:

```text
multiple evidence types
```

or:

```text
one of several equivalent evidence paths
```

These requirements must remain machine-interpretable.

---

## Evidence Completeness

Evidence completeness determines whether sufficient evidence exists to evaluate a rule.

Conceptually:

```text
Required Evidence
       │
       ▼
Available Evidence
       │
   ┌───┴────┐
   ▼        ▼
Complete  Incomplete
```

Incomplete evidence must not produce a false PASS.

---

## Evidence Sufficiency

Evidence may exist without being sufficient.

For example:

```text
One unit test passed
```

does not necessarily satisfy:

```text
Complete capability contract test suite required
```

Sufficiency is determined by the rule's evidence requirements.

---

## Evidence Conflict

Multiple evidence objects may disagree.

For example:

```text
Local Tests: PASS
CI Tests: FAIL
```

The framework must not silently select the favorable result.

Conflict resolution must consider:

* trust level;
* freshness;
* scope;
* profile policy;
* provenance.

Conflicting evidence should remain visible.

---

## Evidence Precedence

Where precedence is required, it must be governed.

A conceptual policy may prefer:

```text
Current Attested Evidence
        >
Current Trusted CI Evidence
        >
Current Local Evidence
        >
Unverified Evidence
```

This hierarchy is illustrative.

The final trust model must be defined explicitly.

---

## Negative Evidence

Evidence may demonstrate a violation.

For example:

```text
Unsupported import detected
```

is valid evidence.

Evidence is not inherently positive or negative.

It records facts.

Rule evaluation determines their compliance meaning.

---

## Absence of Evidence

Absence of evidence is not evidence of compliance.

If a required evidence source is missing:

```text
Required Evidence Missing
        │
        ▼
NOT_EVALUATED
```

or another explicit incomplete state should result.

It must never silently become PASS.

---

## Evidence Store

The Validation Engine should expose an Evidence Store abstraction.

The Evidence Store manages evidence during an evaluation.

Conceptually:

```text
EvidenceStore
├── add
├── retrieve
├── query
├── correlate
├── validate
├── invalidate
└── export
```

The initial implementation may be transient.

The contract should permit future persistent implementations.

---

## Evidence Query

Rules and evaluators should request evidence through structured queries rather than directly depending on individual validators.

Conceptually:

```text
EvidenceQuery
├── type
├── scope
├── plugin
├── trust_requirement
├── freshness_requirement
└── producer_constraint
```

This further separates rule semantics from evidence production mechanisms.

---

## Evidence Correlation

Evidence must be correlatable with:

* Evaluation ID;
* Plugin ID;
* Rule IDs;
* Finding IDs;
* source revision;
* profile;
* certification workflow.

Correlation enables end-to-end traceability.

---

## Evaluation Association

Evidence collected during an evaluation should identify its Evaluation ID.

This provides the relationship:

```text
Evaluation
   │
   ├── Evidence
   ├── Rule Outcomes
   ├── Findings
   └── Compliance Result
```

Imported evidence may also retain its original producer evaluation identity.

---

## Finding Association

A finding should reference the evidence demonstrating the condition.

Conceptually:

```text
Rule
  +
Evidence
  =
Failed Outcome
      │
      ▼
Finding
```

A reviewer should be able to navigate from a finding to the evidence that produced it.

---

## Evidence Reporting

Human-readable reports should summarize relevant evidence without exposing unnecessary raw detail.

Structured reports should preserve evidence references.

Large raw artifacts may remain external and be referenced through stable identifiers or artifact locations.

---

## Evidence Serialization

Canonical evidence must be serializable.

This supports:

* machine-readable reports;
* CI exchange;
* persistence;
* certification workflows;
* future registry integration.

Serialization formats may evolve.

The semantic evidence model must remain stable.

---

## Evidence Privacy

Compliance evidence may contain sensitive information.

Examples include:

* file paths;
* configuration values;
* dependency information;
* security findings;
* environment metadata.

The framework must avoid unnecessarily embedding sensitive values into portable compliance reports.

Evidence collection should follow data minimization principles.

---

## Secret Handling

Secrets must never be stored as ordinary compliance evidence.

Validators encountering secrets should record only the information required to explain compliance.

For example:

```text
Secret detected in prohibited location
```

is appropriate.

The secret value itself must not be copied into the evidence payload.

---

## Evidence Retention

Evidence retention policy may vary according to lifecycle context.

Development evidence may be short-lived.

Release or certification evidence may require longer retention.

Retention policy belongs to governance and infrastructure design.

The Evidence Model must support traceability for whatever retention period applies.

---

## Evidence Portability

Evidence should be portable between FamilyOS engineering systems when appropriate.

For example:

```text
CI
 │
 ▼
Compliance
 │
 ▼
Release
 │
 ▼
Certification
```

Each stage should be able to consume compatible evidence without losing provenance.

---

## Evidence Attestation

Future ecosystem scale may require evidence attestation.

A conceptual model is:

```text
Evidence
   │
   ▼
Canonical Representation
   │
   ▼
Digest
   │
   ▼
Producer Attestation
   │
   ▼
Verifiable Evidence
```

Attestation would allow evidence to cross trust boundaries with stronger integrity guarantees.

---

## Artifact Binding

Evidence used for release or certification should eventually be bindable to a specific plugin artifact.

Conceptually:

```text
Plugin Artifact
      │
      ▼
Artifact Digest
      │
      ├────► Compliance Evidence
      │
      └────► Compliance Result
```

This prevents evidence for one artifact from being applied to another artifact with the same declared version.

---

## Evidence Cache

The framework may support evidence caching.

Cache keys must include all context dimensions relevant to validity.

A simplistic cache key based only on plugin name is insufficient.

A future cache key may incorporate:

```text
Plugin ID
Plugin Version
Source Revision
Platform Version
Validator ID
Validator Version
Configuration
```

Correct invalidation is more important than cache hit rate.

---

## Evidence Comparison

The framework may eventually compare evidence across evaluations.

Examples include:

* new test failures;
* new architecture violations;
* dependency drift;
* documentation regressions;
* compliance drift.

Evidence comparison supports historical analysis without altering previous results.

---

## Evidence History

Persistent environments may maintain evidence history.

Conceptually:

```text
Plugin v1.0
├── Evaluation A
│   └── Evidence Set A
│
├── Evaluation B
│   └── Evidence Set B
│
└── Evaluation C
    └── Evidence Set C
```

History enables compliance evolution analysis and auditability.

---

## Certification Evidence

Certification workflows require evidence stronger than ordinary development feedback.

Certification evidence may require:

* trusted producer;
* exact artifact binding;
* complete provenance;
* accepted framework version;
* accepted profile;
* no unresolved integrity errors;
* accepted freshness.

The certification process determines whether the evidence package is sufficient for certification.

---

## Evidence Package

The framework may eventually support a portable Evidence Package.

Conceptually:

```text
ComplianceEvidencePackage
├── manifest
├── plugin_identity
├── artifact_identity
├── evaluation_context
├── evidence
```

Such a package could support release, registry, and certification workflows.

---

## Evidence Failure Modes

The framework must explicitly handle evidence failure conditions.

Examples include:

```text

Stale Evidence
Corrupted Evidence
Untrusted Evidence
Incompatible Evidence
Conflicting Evidence
Expired Evidence

```

## Evidence Diagnostics

Evidence rejection should explain why it occurred.

For example:

```text

  reason: source revision mismatch
  expected: abc123
  actual: def456
```

Clear diagnostics are essential for developer and CI workflows.

## Evidence Testing

The Evidence Model itself requires tests.

Core test categories include:

* evidence serialization;
* identity generation;
* provenance validation;
* trust validation;
* freshness validation;
* scope validation;
* compatibility;
* reuse;
* invalidation;
* conflict handling;
* secret redaction;
* artifact binding.

Evidence infrastructure is part of the compliance trust boundary.

---

## Evidence Governance

Evidence policy must be governed.

Governance includes:

* accepted evidence types;
* accepted producers;
* trust levels;
* freshness requirements;
* retention requirements;
* integrity requirements;
* manual evidence authority;
* certification evidence requirements.

Individual plugins must not define the trust policy for evidence used to validate themselves.

---

## Evidence Invariants

The Evidence Model establishes the following invariants:

1. Every evidence object has an identity.
2. Evidence identifies its source and producer.
3. Plugin-specific evidence identifies the affected plugin.
4. Context-sensitive evidence records relevant platform context.
5. Evidence scope is explicit.
6. Evidence has traceable provenance.
7. Finalized evidence is immutable.
8. Evidence reuse requires compatibility validation.
9. Stale evidence cannot silently satisfy current requirements.
10. Missing evidence is never equivalent to PASS.
11. Evidence trust is distinct from rule outcome.
12. External evidence requires provenance validation.
13. Conflicting evidence remains visible.
14. Evidence can support multiple rules.
15. Rules may require multiple evidence objects.
16. Findings reference supporting evidence.
17. Secrets are not stored as ordinary evidence payload.
18. Stronger profiles may require stronger evidence provenance.
19. Historical evidence remains associated with its original context.
20. Plugins cannot declare their own evidence trustworthy.

---

## Evidence Summary

The FamilyOS Evidence Model transforms engineering observations into trustworthy compliance inputs.

Its role can be summarized as:

```text
Observation
    +
Identity
    +
Provenance
    +
Context
    +
Scope
    +
Freshness
    +
Integrity
    +
Trust
    =
Compliance Evidence
```

Only evidence satisfying the requirements of the active rule and profile should influence a compliance decision.

---

## Final Evidence Principle

The governing principle of the Evidence Model is:

> Compliance evidence must prove not only what was observed, but also where, when, how, and for which artifact that observation was produced.

This principle allows FamilyOS to build compliance decisions that remain reproducible, auditable, reusable, and trustworthy across development, CI, release, and certification workflows.
