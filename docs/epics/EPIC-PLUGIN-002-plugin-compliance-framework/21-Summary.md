# Plugin Compliance Framework

## 21 Summary

### Introduction

EPIC-PLUGIN-002 establishes the FamilyOS Plugin Compliance Framework.

Its purpose is to make plugin conformance explicit, measurable, reproducible, automatable, auditable, and enforceable across the FamilyOS ecosystem.

The framework defines how platform requirements are translated into governed compliance rules, evaluated against plugin evidence, converted into findings, and ultimately used to determine lifecycle eligibility.

The central principle is:

> A plugin is not compliant because it works. It is compliant because its conformance to the FamilyOS platform contract can be demonstrated.

---

## Strategic Role

The Plugin Compliance Framework sits between plugin extensibility and ecosystem trust.

Its role is to preserve FamilyOS architectural and engineering integrity while allowing the plugin ecosystem to grow.

The strategic progression is:

```text
Plugin Exists
    │
    ▼
Plugin Loads
    │
    ▼
Plugin Works
    │
    ▼
Plugin Is Compliant
    │
    ▼
Plugin Is Release Eligible
    │
    ▼
Plugin Is Certification Eligible
    │
    ▼
Plugin Is Certified
```

Each level represents a stronger assurance claim.

## Compliance Rules

Compliance rules are the smallest governed units of conformance.

Every rule must define:

* stable identity;
* domain;
* normative requirement;
* rationale;
* severity;
* applicability;
* validation strategy;
* evidence requirements;
* remediation;
* ownership;
* lifecycle.

Rules must remain versioned, testable, traceable, and governable.

## Compliance Profiles

Profiles determine which rules apply to a specific plugin and lifecycle context.

The intended profile family includes:

```text
development
experimental
built-in
official
third-party
release
certification
```

Profiles select and compose rules.

They do not redefine rule meaning.

---

## Validation Engine

The Validation Engine provides the execution core of the framework.

Its responsibilities include:

* context construction;
* profile resolution;
* rule resolution;
* dependency analysis;
* validation planning;
* validator execution;
* evidence collection;
* rule evaluation;
* finding generation;
* decision derivation;
* structured result production.

The same engine should be used by local tooling, CI, build, release, and certification consumers.

```text
NOT_APPLICABLE

```

## Severity Model

The baseline severity model is:

```text
INFO
WARNING
ERROR
CRITICAL
```

Severity expresses consequence.

Profiles and gates determine how that severity affects progression.

---

## Compliance Findings

Findings explain concrete compliance conditions discovered during an evaluation.

A finding connects:

```text
Rule
   +
Evidence
   +
Observed Condition
   +
Severity
   +
Remediation
```

Findings must remain actionable and traceable.

They must not become opaque error messages.

---

## Compliance Status

The canonical overall compliance states are:

```text
COMPLIANT
NON_COMPLIANT
INCOMPLETE
ERROR
```

These states summarize the complete evaluation.

They must not be confused with rule outcomes or severity.

* developer-facing text;
* JSON;

* release reports;
* certification packages;
* governance views.

## Compliance Gates

Gates convert Compliance Results into lifecycle decisions.

A gate consumes:

```text
Compliance Result
        +
Gate Policy
        +
Lifecycle Context
        =
Gate Decision
```

Gates do not define new compliance rules.

They enforce the assurance required for progression.

---

## Certification Boundary

Compliance and certification remain separate.

Compliance determines technical conformance.

Certification provides a broader governed trust decision.

The boundary is:

```text
Compliance
    │
    ▼
Certification Eligibility
    │
    ▼
Certification Gate
    │
    ▼
Certification Governance
    │
    ▼
Certification Decision
```

A compliant plugin is not automatically certified.

---

## Governance

The framework treats compliance requirements as governed platform contracts.

Governance covers:

* rule creation;
* ownership;
* review;
* severity;
* applicability;
* activation;
* versioning;
* deprecation;
* retirement;
* exceptions;
* suppressions;
* profile evolution;
* gate evolution.

Compliance policy must never emerge accidentally from validator behavior.

---

## Security and Trust

The framework assumes the evaluated plugin is not automatically trusted.

The compliance trust boundary protects:

* rules;
* profiles;
* validators;
* evidence trust;
* compliance decisions;
* gate policy.

Plugins may provide inputs.

They must not control the mechanisms that decide whether those inputs demonstrate compliance.

## Key Invariants

The framework establishes several non-negotiable invariants:

1. Compliance is explicit.
2. Compliance is evidence-based.
3. Rules have stable identities.
4. Profiles select rules without redefining them.
5. Validators do not define policy.
6. Missing evidence never becomes PASS.
7. Validator errors remain distinct from plugin failures.
8. Severity and rule outcome remain separate.
9. Compliance status is derived.
10. Exceptions and suppressions remain visible.
11. Mandatory requirements cannot be silently bypassed.
12. Reports derive from structured results.
13. Local and CI compliance use the same semantics.
14. Certification remains separate from compliance.
15. Plugin origin does not substitute for evidence.
16. Historical results remain immutable.
17. Framework evolution is versioned and governed.
18. Plugins cannot redefine the compliance policy governing themselves.

When EPIC-PLUGIN-002 is operational, FamilyOS should be able to evaluate a supported plugin and answer clearly:

```text
Which profile was evaluated?
Which rules applied?
Which rules passed?
```

These questions should be answerable through structured, reproducible compliance evidence.
