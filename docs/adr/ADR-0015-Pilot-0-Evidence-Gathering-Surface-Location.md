# ADR-0015 — Pilot 0 Evidence-Gathering Surface Location

| Field | Value |
| --- | --- |
| ADR | ADR-0015 |
| Version | 1.0.0 |
| Status | Accepted |
| Date | 2026-09-18 |
| Scope | Pilot 0 runtime location only |

## Context

FamilyOS's AI-governance foundation is established by ADR-0014, RFC-0017, RFC-0018, and SPEC-0016.

`familyos-cli` is the repository's engineering, generation, and validation tooling. It is not a running FamilyOS product surface.

The next phase is intentionally pilot-driven. FamilyOS needs real product evidence from a small Pilot 0 before additional architecture or generation abstractions are justified.

## Decision

Pilot 0 SHALL be implemented outside `familyos-cli`, in a separate, hand-authored product surface.

The purpose of this surface is to gather real product evidence rapidly while preserving the existing FamilyOS governance boundaries.

`familyos-cli` SHALL remain engineering, generation, and validation tooling for this decision.

Pilot 0 SHALL NOT import `familyos-cli` internal implementation modules as product-runtime dependencies.

## Scope of This Decision

This decision establishes only the location and temporary role of Pilot 0:

- Pilot 0 lives outside `familyos-cli`.
- Pilot 0 is a hand-authored evidence-gathering product surface.
- `familyos-cli` remains engineering, generation, and validation tooling.
- Pilot 0 may follow accepted FamilyOS architectural contracts as design references without redefining them.
- Pilot 0 exists to generate product evidence before further abstraction.

## Explicitly Not Decided

This ADR does not:

- define the final FamilyOS product-runtime architecture;
- replace, supersede, or amend ADR-0014;
- create any new authorization authority;
- authorize runtime implementation by itself;
- authorize merge, release, or deployment;
- authorize the use of real family data;
- decide whether a future validated FamilyOS product shall be generated by `familyos-cli`;
- require Pilot 0 to reuse `familyos-cli` internal `PluginCapability` or runtime implementation code;
- resolve SPEC-0016-R20 or define Workflow internal state or process representation.

Pilot 0 human-confirmation mechanisms are evidence-gathering mechanisms only and SHALL NOT be interpreted as the normative FamilyOS Workflow or Security/Identity architecture.

## Evidence-Before-Abstraction Constraint

Pilot 0 SHALL prefer the minimum architecture required to produce useful family-facing evidence.

Additional abstractions SHOULD be introduced only when they directly support Pilot 0 capability, safety, validation, or evidence gathering.

The existence of Pilot 0 SHALL NOT be used as evidence that its provisional internal design is the final FamilyOS platform architecture.

## Revisit Trigger

This decision SHALL be revisited after Pilot 0 produces real product evidence.

The revisit SHALL consider at minimum:

- observed family usage;
- pilot retention signals;
- conflict-detection usefulness;
- trust and authorization failures;
- operational cost;
- model-provider cost;
- privacy and consent findings;
- willingness-to-pay evidence; and
- whether the validated product shape justifies a generated-product model managed by `familyos-cli`.

## Consequences

### Positive Consequences

- Pilot 0 can move toward family-visible value without placing live product concerns inside the CLI.
- Existing FamilyOS governance contracts remain available as design references.
- Generation tooling is deferred until product evidence justifies it.
- The final runtime architecture remains explicitly open.

### Trade-offs

- A separate Pilot 0 surface must be governed and maintained during the pilot.
- Some pilot code may later be replaced or formalized after evidence is collected.
- Contract reuse is initially conceptual and normative rather than a direct import of `familyos-cli` internals.

## Authorization Boundary

Filing this ADR records the bounded location decision only.

It does not authorize:

- Pilot 0 runtime implementation;
- repository merge;
- release or deployment;
- use of real family data;
- onboarding of pilot families; or
- any change to existing authorization authority.

Those actions require separate explicit authorization and, where applicable, satisfaction of the Pilot 0 privacy and consent gates.
